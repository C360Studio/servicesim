# Exa Agent-run contract audit, 2026-10-01

Record of the contract-drift audit behind issue #8 (Exa half) and of the fixes that followed it. It covers the three
Exa agent routes only — `POST /agent/runs`, `GET /agent/runs/{id}` and `HEAD /agent/runs/{id}` — and nothing else the
Exa profile simulates. A reader with the spec below and this file can reproduce every claim.

**To reproduce.** Fetch the URL, then run `shasum -a 256 exa-spec.yaml` and compare. An identical hash means every
line number in this file applies. A different hash means the vendor changed the document after this record: the
schema names below (`AgentRun`, `AgentCostDollars`, …) still locate the regions, but the line numbers will have
moved and the findings need re-reading. The fetched bytes are not committed: whether the vendor's document may be
redistributed is an open question (see the repository's root `contracts/README.md`).

House rule 1 applies: the verified contract wins over every other document in this repository, and for these routes
that now means the spec wins over the prose of `profiles/exa/contracts/README.md`, which was read from the vendor's
prose pages on 2026-08-15.

## Method and limits

- **Read-only audit first, then fixes.** A lead list from a read-only audit was re-verified against the spec region by
  region before any code changed. No vendor API was called.
- **What "changed" means here.** The bytes of the 2026-08-16 spec this profile was last checked against were not kept
  (only their hash), so "what changed since that snapshot" is not determinable. Every classification below is the
  difference between **this spec** and **the profile before this unit**.
- **Only the agent surface was re-read.** The spec covers all seven Exa routes, but this audit read only the three
  agent routes against it. `POST /search`, `/answer`, `/contents` and `/findSimilar` were not re-read: they keep their
  earlier per-entry `verified:` dates, and the provider-level date in `provenance.yaml` and the root
  `contracts/README.md` — 2026-10-01 for this audit, 2026-10-02 since the cancel addendum below — is the date
  `contracts.Conform` forces, not a claim about those routes. That re-read is owed and is tracked in issue #11.
- **The spec has no example bodies.** It fixes which keys exist, which are required and their types, but gives no
  sample response. Wherever a value, a pairing or a runtime behaviour is not stated, it is classified
  SIMULATOR-POLICY, INFERENCE or UNVERIFIED, never VERIFIED, and it is never presented as a vendor guarantee. This
  holds above all for billing and metering.
- **Other Exa routes were not re-read.** `provenance.yaml`'s `spec.sha256` now records this fetch, but only the six
  `exa-agent-runs-*` entries were re-read against it. `/search`, `/answer`, `/contents` and `/findSimilar` keep their
  earlier `verified` dates and owe a re-read of their own.

## Breaking changes this unit made

Servicesim is greenfield with one known user, and the owner approved breaking wire corrections with no shims.

1. The create answers `200`, not `201`. A scenario fault attempt that pinned `status: 201` on an Exa create needs
   `status: 200`.
2. Run ids are `agent_run_` plus 32 hex characters (42 characters), not `run_` plus 32 hex.
3. `effort: max` is rejected with a 400 and `ultra` is accepted. Any other off-enum or non-string `effort`, `null`
   included, is a 400.
4. The run object is the spec's ten keys on every response. `output`, `usage` and `costDollars` now appear on queued
   and running runs; `object`, `completedAt` and `request` are new; `costDollars` gains `agentCompute`, `search`,
   `emails` and `phoneNumbers`; `usage` gains `searches`, `emails` and `phoneNumbers`.
5. `costDollars.search` is emitted as a number. It was deliberately absent.
6. Grounding citations are `{url, title}`: the `id` key is gone. `citations` is always present.
7. The run-level `error` object is gone from the wire. A scenario that declares `error:` on an agent-run turn is a
   load error, `exa.agent_run.error.not_in_schema`. The finding `exa.agent_run.failed_without_error` and its exported
   constant `CodeAgentRunFailedWithoutError` are removed: a failed run needs only `status: failed`.
8. Every error on the three agent routes is `{"error": {"type", "code", "message"}}`, not the flat
   `{requestId, error, tag}` body, and carries an `x-request-id` header. The other Exa routes are unchanged.
9. A fault attempt's `tag:` on an agent route becomes the error `code`, and `error:` the `message`. A `tag:` outside
   the ten-member code enum is still rendered, and is warned about at load (`exa.agent_run.fault_tag.unknown`).
10. `usage.data_sources` counts are integers; a fractional scenario value is now a load error, and so is a negative or
    non-finite `usage` or `cost_dollars` value of any kind (`exa.agent_run.value.range`).
11. `budget.maxDurationSeconds` and `budget.maxCostDollars` are rejected with a 400 when mistyped. When out of range
    they are a 400 only if the spec says the limit applies to the request's effort (`maxCostDollars` on `auto` and
    `ultra`, with an omitted `effort` counting as `auto`; `maxDurationSeconds` on `ultra`), and a warning otherwise.
    The effort scoping is SIMULATOR-POLICY.
12. A scripted `cost_dollars` now renders on a non-terminal snapshot that declares it. Before, `costDollars` was dropped
    from every non-terminal snapshot even when scripted.

New scenario keys: usage `searches`, `emails`, `phone_numbers`; cost `agent_compute`, `search`, `emails`,
`phone_numbers`. New finding code: `exa.agent_run.error.not_in_schema`. New request-time finding codes:
`exa.budget.maxDurationSeconds.range` and `exa.budget.maxCostDollars.range`; `exa.effort.invalid` is now an error
rather than a warning. New load-time codes: `exa.agent_run.value.range` and `exa.agent_run.fault_tag.unknown`.

## Where this record disagrees with the lead audit

The lead list's spec readings all held up against the spec; the differences are in classification and detail.

- **`x-request-id` was left unchecked** for whether `provider.Response` can carry headers. It can (the `Header` field
  the fault executor already merges), so it was implemented without an exported-surface change.
- **The `budget` ranges are prose, not keywords.** The lead list called the ranges simply "number, $1-$100" and
  "integer, 300-10,800". The spec states them only in the description text, which is why the rejecting status is
  SIMULATOR-POLICY and why the "only for `auto`/`ultra`" clauses are read as scoping the range check rather than as
  something to reject: a request under another effort is served and the finding is a warning.
- **`effort: null` and non-strings** are rejected too; the lead list considered only off-enum strings.
- **`usage.dataSources` integers.** The lead list noted the integer typing; the profile now enforces it at load.
- **Three leads were not acted on:** a streamed create (`Accept: text/event-stream`), the `Exa-Beta` header and the
  malformed-id 400 are UNVERIFIED and stay unsimulated; the first two are not needed to make any response conform and
  the third has no stated trigger.

## Cancel, 2026-10-02

An addendum for the cancel route (issue #6, unit U4), read against the same document.

- **The spec.** Re-fetched 2026-10-02 from <https://exa.ai/docs/exa-spec.yaml>; sha256
  `cbb9a1429456270527cec49cb495ec00671dd2b7702c411a168988e22222416d`, **identical** to the 2026-10-01 fetch above, so
  nothing recorded in this audit moved. Read: `cancelAgentRun` (lines 1153-1241) and `stopAgentRun` (lines 1242-1330),
  with `AgentRunId`, `AgentRun` and `AgentErrorResponse` as already recorded.
- **What the spec says.** `POST /agent/runs/{id}/cancel`, the id its only parameter and **no `requestBody`**; `200` is
  an `AgentRun`; errors `400`, `401`, `404`, `429` and `500`, all `AgentErrorResponse` with `x-request-id`. "Cancel a
  queued or running Agent run immediately without returning any results. You are billed for usage accrued before
  cancellation. If the run has already reached a terminal status, the API returns the existing run." (line 1157)
  `/stop` is a separate operation, `ultra`-only, which completes a run early with its results.
- **What changed in the profile.** The cancel route is served, on its own fault key (`exa:agent_runs.cancel`) and a
  per-run lane, planned by `cancel.fault`. A cancel answers exactly the snapshot the run's next poll returns; a run
  whose next poll is terminal is returned as it is and nothing is recorded (the spec's "returns the existing run",
  judged by the next poll — SIMULATOR-POLICY). No body is read. A cancel the scenario cannot answer is a `500`
  `SERVER_ERROR` (SIMULATOR-POLICY for when). Journal labels: `exa.agent_runs.cancel.accepted` only for a recorded
  cancel, `…cancel.repeated`, `…cancel.terminal` and `…cancel.unrecorded` otherwise, and the poll label is now
  `exa.agent_runs.polled.<status>` (it was `exa.agent_runs.polled`). Every terminal snapshot without a scripted
  `cost_dollars` raises the load warning `exa.agent_run.cost_unscripted` (ruling 6). `/stop` stays unsimulated and is
  not aliased. Four goldens were added (`exa-agent-runs-cancelled.json` and the cancel `401`, `404` and `500`), each
  `verified: 2026-10-02`.
- **The dates moved for one reason only.** The provider-level `verified:` (in `provenance.yaml` and the root
  `contracts/README.md` index) and `spec.retrieved` moved to 2026-10-02 because `contracts.Conform` forces them: the
  provider date may be no older than any entry, and the four cancel entries are 2026-10-02, and `spec.retrieved` may
  be no earlier than the provider date. It is not a re-read of the other routes: `POST /search`, `/answer`,
  `/contents` and `/findSimilar` were not read against this fetch, and that re-read is still owed (issue #11).
- **The full record** is the "Cancel" section of
  [`profiles/exa/contracts/README.md`](../../profiles/exa/contracts/README.md#cancel-post-agentrunsidcancel).
